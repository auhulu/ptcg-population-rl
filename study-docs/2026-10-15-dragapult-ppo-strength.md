# ドラパルトのPPO更新前後の強さを比較する

2026年10月15日実施。[PPOの1サイクル目](2026-10-15-dragapult-ppo.md)では、240試合の収集と32回の更新、C++対戦の動作確認を行った。今回は更新前後を固定し、共通の相手・seed・席で比較した。元の実装とルートREADMEは変更していない。

2,200試合がエラー0で完了した。5固定相手に対する平均スコアは更新前28.60%から更新後25.45%へ低下し、差は−3.15ポイント、95%信頼区間は−6.30〜+0.05ポイントだった。今回のPPO更新による改善の証拠はなく、点推定では悪化傾向がある。ただし区間は0を含むため、悪化が確定したとも結論づけない。

## 比較するモデルと対戦条件

| 呼称 | C++モデル |
|---|---|
| 更新前（before） | `outputs/dragapult/distillation_v1/model/model.bin` |
| 更新後（after） | `outputs/dragapult/ppo_v1/cycle-000/models/model.bin` |

評価中はモデルを更新しない。学習収集時の確率的選択と異なり、評価では既存arenaの決定的な選択を使う。この結果は、その選択方法と今回の固定相手集合についての比較となる。

5相手それぞれについて100個のseedを用意し、同じseedで両席をプレイする。更新前200試合・更新後200試合で、5相手の合計は2,000試合。さらに更新後対更新前の直接対決を100 seed・両席で200試合行う。総計2,200試合となる。

| 相手 | agent名 | seed範囲（両席・更新前後で共通） |
|---|---|---|
| メガルカリオexのルール方策 | `mega_lucario` | 203000000〜203000099 |
| ドラパルトexのルール方策 | `dragapult` | 204000000〜204000099 |
| ナンジャモのルール方策 | `iono` | 205000000〜205000099 |
| メガユキノオーexのルール方策 | `mega_abomasnow` | 206000000〜206000099 |
| ドラパルトexの固定GBDT | `dragapult_gbdt` | 207000000〜207000099 |
| 更新前Transformer（直接対決） | `dragapult_transformer` | 204000000〜204000099 |

GBDTは `outputs/dragapult/imitation_v2/model/model.gbdt`。直接対決は別の対戦集合であり、seedの数値はルール方策ドラパルトとの対戦集合と重なる。5固定相手の各集合とは混ぜて集計しない。

比較の1単位は同じ相手・seedの両席である。初期乱数と席を揃えても、方策が違えばその後の行動・局面は変わる。共通seedは対戦全体を同じ展開に固定するものではない。

## 集計と不確実性

勝ちを1、引き分けを0.5、負けを0とするスコアを集計する。引き分けがある場合、この平均スコアは単純な勝率とは異なる。

更新前後の差は、相手・seedごとに両席の平均スコアを取り、その差を計算する。bootstrapでは個々の試合を独立に扱わず、同じseedの両席と更新前後の対応を維持して再標本化する。5固定相手の総合値は各相手を均等に重みづけし、直接対決は別に計算する。

- 再標本化は50,000回、乱数seedは204。
- 5相手の総合差と各対面の差は95%信頼区間を示す。
- 5対面を同時に確認するため、各対面にはBonferroni補正に対応する99%信頼区間も示す。
- 直接対決は更新後側の平均スコアと95%信頼区間を示し、互角の0.5と比較する。

改善を判断するには点推定だけでなく区間を見る。区間が0を含む更新前後差について、改善・悪化が確定したとは扱わない。総合値が改善していても対面ごとの悪化を確認する。エージェント・エンジンエラーは別に集計し、問題があれば勝敗の解釈と切り分ける。

信頼区間はpercentile bootstrapによる近似である。Bonferroni補正も名目上の同時被覆率95%に対応する設定であり、その被覆率を厳密に保証するものではない。これは今回のseed集合と固定相手分布に基づく不確実性の推定であり、すべてのデッキや未知の相手への強さを保証しない。同じ学習を別seedでやり直した際のばらつきも含まない。PPOのholdout KL診断とも異なり、新しい対戦結果を使った比較である。

## 並列実行と環境

外側で8個の対戦組み合わせを並列実行し、各 `rating_arena` の `workers` は1にした。BLAS・OpenMPスレッド数も各1。更新前後×5相手と直接対決の計11組を処理する。1組は両席の各100試合で、内側の1ワーカーが順次処理する。

CPUはRyzen 7 5700X（8コア・16論理CPU）、メモリは約47 GiB、OSはWSL2上のLinux。推論と対戦はCPUで行った。記録された経過時間は60.69秒で、範囲は2,200試合の収集と組み合わせごとのrating推定であり、PPO学習・rollout抽出・今回のbootstrap集計は含まない。4・8・12並列の速度比較は行っていないため、並列化による速度向上率や最適並列数は主張しない。

## 既存コマンドで再現する

リポジトリ直下から、ビルド済み `build/arena_cpp` と上記モデルを用意して実行する。実行に使用した補助スクリプトはGit管理対象外だが、収集は既存の `src/tools/rating_arena.py` だけで再現できる。

たとえば `outputs/dragapult/ppo_strength_v1/after_mega_lucario.json` に次のrosterを置く。モデルの相対パスはリポジトリ直下ではなく、roster JSONのあるディレクトリを基準に解決される。

```json
{
  "candidate": {
    "agent": "dragapult_transformer",
    "model": "../ppo_v1/cycle-000/models/model.bin"
  },
  "opponent": {
    "agent": "mega_lucario"
  }
}
```

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 \
.venv/bin/python src/tools/rating_arena.py \
  --roster outputs/dragapult/ppo_strength_v1/after_mega_lucario.json \
  --output-dir outputs/dragapult/ppo_strength_v1/after_mega_lucario \
  --games-per-pair 200 --seed 203000000 --workers 1 --raw-bt
```

この呼び出しは200試合を同じ100 seedの両席に配分する。既存の成果物を上書きしないよう、新規の出力先で実行する。対戦記録の続行には、同じモデル・エンジン・roster・seedで `--resume` を指定する。

残りの10組も同じ形式でrosterと出力先を作る。

- 更新前の5組では `candidate.model` を `../distillation_v1/model/model.bin` にする。更新後の5組では上記のPPOモデルを使う。
- 相手の `agent` と `--seed` は対戦条件の表に従う。GBDT相手には `"model": "../imitation_v2/model/model.gbdt"` を追加する。
- 直接対決の `candidate` は更新後、`opponent` は更新前の `dragapult_transformer` とし、`--seed 204000000` を使う。
- 全組で `--games-per-pair 200 --workers 1 --raw-bt` を使い、独立したコマンドを最大8個まで同時に実行する。

`rating_arena` はratingレポートも生成するが、この比較の主指標は `games.jsonl` から集計する対応のあるスコア差である。2者だけで推定した別々のratingを、相手をまたいで単純比較する用途には使わない。

## 結果と成果物

全2,200試合のエージェント・エンジンエラーは0。更新前後で相手・seed・席の対応が一致し、全11組のmanifestに保存されたモデル・エンジン・デッキのSHA-256も確認した。

以下の勝敗表記は「勝ち / 引き分け / 負け」。各対面は更新前後それぞれ200試合で、平均スコアには引き分けを0.5勝として含める。

| 相手 | 更新前の勝敗 | 更新後の勝敗 | 更新前スコア | 更新後スコア |
|---|---:|---:|---:|---:|
| メガルカリオex | 59 / 0 / 141 | 46 / 1 / 153 | 29.50% | 23.25% |
| ドラパルトex | 36 / 0 / 164 | 38 / 0 / 162 | 18.00% | 19.00% |
| ナンジャモ | 65 / 0 / 135 | 50 / 0 / 150 | 32.50% | 25.00% |
| メガユキノオーex | 36 / 0 / 164 | 40 / 0 / 160 | 18.00% | 20.00% |
| ドラパルトexのGBDT | 90 / 0 / 110 | 80 / 0 / 120 | 45.00% | 40.00% |
| **総合** | **286 / 0 / 714** | **254 / 1 / 745** | **28.60%** | **25.45%** |

ナンジャモ対面の未補正95%区間は負だが、5対面の比較を考慮した99%区間では0を含む。すべての対面で補正後の区間が0を含んでおり、特定対面の改善・悪化を確定したとは扱わない。

直接対決は更新後が94勝・0引き分け・106敗で、平均スコア47.0%、95%信頼区間40.5〜53.5%。互角の50%を含み、ここでも更新後が強くなった証拠は得られなかった。

今回の結果から、学習損失が計算できて重みが変わったことだけでは強さの改善を示せないとわかる。PPO更新時のholdout近似KLは0.038358だったが、それだけで成績低下の原因を断定できない。次の候補は更新回数や学習率を減らした比較であり、同じ初期モデルから条件を変えて評価する。今回の作業では追加学習は行っていない。

C++モデルのSHA-256は、更新前 `8729fd5d105e08d2b0338c01003f1f283e572bfd693df6fe884d51f163a24013`、更新後 `7c83a626580995681c5b8b090a12f77a0eff0281f465cabc4b8255032d658835`。これは `.bin` のハッシュであり、PPO学習記録の `.pt` のハッシュとは異なる。
